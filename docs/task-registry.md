# 活动任务登记：0.1.0-p0.2 候选设计

执行器需要回答两个问题：这个任务是否仍属于当前 runtime，以及任务结束后应该移除哪一个登记。此前使用 `HashMap<u64, Arc<Task>>`，任务编号用于散列查找。本候选改用 `Vec<Arc<Task>>`，让登记、唤醒检查和完成移除直接访问数组。实现见 [执行器](../crates/zrun-executor/src/lib.rs) 与 [任务对象](../crates/zrun-task/src/lib.rs)。

数组保存的是引用计数指针，Future 仍留在原来的任务分配中。移动数组元素不会移动 Future，也不会改变任务的单调递增编号。该改动减少了这些路径上的散列操作；具体吞吐与 RSS 变化必须由同配置实验确认。

## 索引不代表身份

每个 Task 增加一个 `AtomicUsize`，记录当前数组位置。未登记或已移除时取 `usize::MAX`。该字段只是查找提示，不能单独证明数组位置仍属于这个任务。

| 操作 | 持有登记锁时的步骤 |
| --- | --- |
| 接收任务 | 检查关闭状态、容量及编号上限；写入数组末尾索引，再把任务引用加入登记与就绪队列 |
| 接收唤醒 | 读取索引，检查边界，并用 `Arc::ptr_eq` 比较该位置与传入任务的实际对象身份 |
| 任务结束 | 检查索引与对象身份；用 `swap_remove` 移除引用，把尾部移入的任务索引更新为新位置 |
| runtime 关闭 | 在同一把锁内关闭入口并取出整个登记和就绪队列；解锁后终止任务和释放引用 |

登记索引的读写都发生在执行器的登记互斥锁内。锁负责发布数组内容及位置变化；原子字段使用 Relaxed，只保证字段本身可以安全存储和读取，不承担 Future 所有权或调度状态的同步。任务状态仍由原有状态机和任务锁保护。

移除时先把被移除任务的索引设为无效，再更新被移动任务的索引。其他线程必须取得登记锁才能检查或改变数组，因此看不到这两步之间的登记状态。被移除的最后一个登记引用在解锁后释放，避免析构代码重入 runtime 时死锁。

## 旧唤醒与容量复用

一个已经完成的任务可能仍被外部 Waker 持有。完成状态阻止它重新调度；登记检查还会核对真实对象身份，因此旧索引不能把新任务当作原任务。只要旧引用仍在，原 Task 分配仍然存活，地址比较不会把已经释放的指针当作有效对象使用。

任务退出后，数组长度减少一个，下一次 spawn 可以复用空出的容量。容量限制依据当前活动任务数，不依据历史任务总数。数组按需增长，并可能保留先前分配的容量；这不等于零分配，也不意味着空闲 RSS 一定下降。任务头、Future、结果和就绪队列仍各有自己的存储成本。

本候选不新增 unsafe，不改变 RawWaker 引用计数、Future 的唯一 poll 所有权、单线程执行、每批 64 次 poll 的公平性预算或休眠通知协议。内部、隐藏于文档的 `Scheduler::finished` 回调由任务编号改为 `&Task`，以便核对对象身份；直接实现这个内部 trait 的代码需要一起更新。应用入口 `Runtime`、`Spawner`、`JoinHandle` 的接口不变。

## 验证边界

新增回归覆盖中间任务先完成、尾部任务移动后继续唤醒、取消后复用容量，以及旧 Waker 在容量复用后保持无效。常规测试重复非顺序完成 64 轮，Miri 下重复 4 轮。原有跨线程唤醒、取消风暴、panic、定时器与关闭回归继续运行。

候选源码实际通过 45 项常规测试、37 项核心 Miri 检查、严格 Clippy 与格式检查。3 项 Loom 检查运行的是现有休眠通知协议；它们不构成新数组登记的穷举模型证明。源码哈希、工具版本、原始日志与随后进行的配对性能实验另存为验收证据。普通测试中默认忽略的百万任务用例不能仅凭上述测试总数记为通过。

性能比较以保留休眠优化的同一基线为对照，隔离本次登记改动。每个规模和场景运行 10 对相邻、交替顺序的新进程，记录全部成功与失败样本；吞吐、延迟和 RSS 分开报告。它比较两个 zrun 修订，不重新证明相对 Tokio 的性能门槛。多 worker、TCP、跨平台和 24 小时稳定性仍按 [阶段计划](plan.md)单独验收。本候选尚未发布或部署。

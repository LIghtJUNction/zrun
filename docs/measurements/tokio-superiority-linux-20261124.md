# Linux 同版本 Tokio 优势验收

候选为 `7501a32`。使用同一源码构建 release 的任务和 TCP 比较器，Tokio 对照锁定为 1.54.1，构建使用 Rust 1.100.0，运行于 Intel Core i9-12900HX 和 Linux 7.3.5-arch1-1。每个配置 10 对独立进程，逐轮交换执行顺序。判定采用配对 bootstrap 95% 区间，TCP 吞吐、TCP P99 和唤醒 P99 按严格领先判断。[验收条件](../design.md#性能验收协议)

## 运行时

1、4、8 worker 和 10,000、100,000 tasks，运行 spawn/join、自唤醒、唤醒延迟、等待中内存及空闲 RSS。600 个样本均通过任务数、标识与结果校验。进程固定在逻辑 CPU 0–15。新 CPU 指标取自唤醒计时间隔内所有线程的进程 CPU 时间，按已校验的唤醒数归一化。

以下是 100,000 tasks 时 zrun/Tokio 的中位数比值。吞吐越高越好，其他列越低越好。

| worker | spawn/join 吞吐 | 唤醒吞吐 | CPU / wake | 唤醒 P99 | 等待中 RSS / task | 空闲增量 RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.618 | 0.736 | 1.359 | 0.022 | 1.030 | 0.760 |
| 4 | 0.327 | 0.212 | 4.215 | 0.067 | 0.992 | 0.866 |
| 8 | 0.312 | 0.305 | 3.616 | 0.028 | 0.991 | 0.876 |

36 个指标配置中，只有 6 个自唤醒 P99 配置通过。4 和 8 worker 在 100,000 tasks 下的 CPU / wake 比值区间分别为 3.498–5.181 和 3.283–4.120。这个 CPU 结果覆盖相同的调度负载，未分解到函数。唤醒 P99 测量本负载中的自唤醒。

## TCP

1、4、8 worker，各测四种连接/帧大小，共 240 个样本完成双端回显校验。服务固定在逻辑 CPU 0–7，相同客户端固定在 8–15。24 个指标配置中，只有 8 worker 的两项 P99 通过。

| 并发连接 | 帧大小 | P99 比值 | 95% 区间 |
| ---: | ---: | ---: | ---: |
| 64 | 64 B | 0.806 | 0.586–0.985 |
| 128 | 4 KiB | 0.738 | 0.593–0.891 |

全部 TCP 吞吐配置尚未通过严格领先门槛。完整范围还需其他 worker/任务规模和目标平台的证据。当前版本未全面超过 Tokio。

原始报告在 Project Z 的 `dist/zrun-superiority-runtime/report.json` 和 `dist/zrun-superiority-tcp-evidence/report.json`。运行时比较器 SHA-256 为 `bb56dcc71d26c3c6768428c2433a2d8fbc6c98b271b793ceac231f3ade8e669c`，TCP 比较器为 `32ff11febe2acf99c8231d5fcf1f676546a0de19e65a1fbed135d5fb5b4f815a`。用同一候选的 Linux CLI 另跑一次 4 worker、1,000 Unix 客户端的负载，验证复用组执行 1 次、合并 999 次。

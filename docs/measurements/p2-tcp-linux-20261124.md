# Linux TCP 与 Unix 命令服务

候选源码为 `ee0e2b5de34f8698f67e947c3cfa5c225ca39d97`。测试在 Intel Core i9-12900HX、24 逻辑 CPU、Linux 7.3.5-arch1-1 和 Rust 1.100.0 上以 release 配置运行。Tokio 比较版本为 1.54.1。

## TCP

服务进程独立启动，复用同一个以 4 个线程运行的回显客户端。服务端固定在逻辑 CPU 0–7，客户端固定在 8–15。一对样本的先后顺序逐轮交替。每格 10 对样本，共 160 次，全部通过帧校验。吞吐按有效 payload 字节计，P99 取客户端消息往返延迟。区间是 5,000 次配对 bootstrap 的 95% 区间。[复现协议](../benchmark-protocol.md)

| worker | 并发连接 | 帧字节 | 吞吐比 zrun/Tokio | P99 比 zrun/Tokio |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 64 | **1.047 [0.976, 1.119]** | 1.062 [0.872, 1.458] |
| 1 | 64 | 64 | **0.966 [0.962, 1.021]** | 0.994 [0.795, 1.339] |
| 1 | 128 | 4,096 | 0.982 [0.949, 1.031] | 1.053 [0.886, 1.211] |
| 1 | 32 | 65,536 | 0.961 [0.909, 1.028] | 0.835 [0.673, 1.177] |
| 4 | 1 | 64 | 0.760 [0.715, 0.843] | 1.618 [1.132, 2.103] |
| 4 | 64 | 64 | 0.964 [0.904, 1.020] | 1.117 [1.017, 1.282] |
| 4 | 128 | 4,096 | 1.036 [0.942, 1.070] | 0.991 [0.847, 1.169] |
| 4 | 32 | 65,536 | 0.898 [0.768, 0.950] | 1.114 [0.948, 1.390] |

加粗表示区间下界达到 0.95 吞吐门槛。P99 的区间上界均超过 1.10。单连接 64 字节用例仍是 4 worker 下的主要差距。

另用相同客户端比较新版单 worker 与 `3378f27` 使用专用 I/O 线程的版本。80 次独立样本全部通过。单连接 64 字节用例吞吐为原来的 1.275 倍，区间 [1.200, 1.342]。P99 为原来的 0.655 倍，区间 [0.481, 0.893]。其他三个用例的吞吐与 P99 区间均包含 1。另测了用就绪代次跳过等待者锁的改动，关键用例的区间均包含 1，已撤回。

TCP 工作区原始文件位于 Project Z 的 `dist/zrun-p2-tcp-{baseline,epoch-pairs,inline-pairs,final}-20261124/report.json`。比较器二进制 SHA-256 为 `e20226a95fea29d2035980cb1e3170c0ab464935baba538b3f413baa6c263ba2`。

## Unix socket 命令服务

在 1 与 4 worker 下各跑 3 对样本。每次释放 1,000 个独立 Unix socket 客户端，提交 `sleep 0.05; printf zrun` 并核对 RPC ID、退出状态和 stdout。对照组各执行 1,000 次，复用组均记录 1 次执行和 999 次合并。

| worker | 独立执行中位用时 | 集中复用中位用时 | 峰值直接子进程数 | 服务线程数 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1.715 s | 0.109 s | 32 → 1 | 2 |
| 4 | 1.719 s | 0.111 s | 32 → 1 | 7 |

服务进程采样峰值 RSS 的中位数，1 worker 为 9,264 → 9,796 KiB，4 worker 为 9,512 → 9,920 KiB。该采样只覆盖服务进程，整组子进程的总内存未测量。原始样本位于 `dist/zrun-sock-final-load-w1.jsonl` 和 `dist/zrun-sock-final-load-w4.jsonl`。

工作区测试 59 项通过、1 项按配置跳过。新版复验了跨线程唤醒、持续可运行任务下的 I/O、默认路径、目录及 socket 权限、重复启动、SIGTERM 清理和跨 TCP、Unix、stdio、CLI 的缓存共享。格式、严格 Clippy、rustdoc 和 release 构建通过。Linux 命令在真实 zmem interactive scope 中读回了自己的 cgroup。

官方 MCP Python SDK 1.27.2 通过 TCP、Unix 和 stdio 转发分别完成了初始化、工具发现和命令调用。另用 Project Z 的 zmcpio 0.5.3（`9c1d8dfaf8432375de7f20dad74d756f2d52089d`）直接连接默认 Unix socket，协商 MCP 2025-11-25，发现 `shell_run` 并验证 stdout。

## 非阻塞写入尝试

基线 `199cf79`。候选在检查 reactor 未关闭后先尝试非阻塞写入；只有遇到背压才登记唤醒器，并在登记后重试以避免漏掉就绪事件。读侧保持原有握手。候选通过全量工作区测试和严格 Clippy，包括超出管道容量的实际写入回归。

同一 Linux 主机、Rust 1.100.0 release，服务端 CPU 0–7、同一负载生成器 CPU 8–15。1 和 4 worker 各跑四种原有连接与帧大小组合，64 KiB 用例每连接 300 帧。每格 12 对独立进程，192 个样本全部通过回显校验。八格吞吐、往返 P99 和合计服务进程 CPU ticks 的配对 95% 区间均包含持平。4 worker 单连接 64 B 的吞吐比为 0.986 [0.937, 1.073]，P99 比为 1.084 [0.853, 1.299]，进程 CPU 比为 1.000 [0.889, 1.125]。进程 CPU ticks 采样精度有限，不能单独隔离唤醒器操作。没有测出可确认的端到端收益，候选未合入。

原始记录位于 `dist/zrun-io-write-first-pairs/report.json`，候选补丁位于 `dist/zrun-io-write-first.patch`。

## 四 worker 小包回显的线程交接

对照二进制由 `199cf79` 构建，同一进程入口选择 zrun 或 Tokio 1.54.1。四 worker，单连接，60,000 个 64 B 请求与 8 个预热帧。服务端 CPU 0–7，客户端 CPU 8–15。同机 Linux x86_64、Rust 1.100.0 release，12 对交替运行的独立进程。24 个样本均通过回显与帧数校验。服务端 CPU 与上下文切换取服务端进程的 `wait4` 资源计数，客户端单独执行。比值区间为 5,000 次配对 bootstrap。

| 指标 | zrun 中位数 | Tokio 中位数 | zrun/Tokio 及 95% 区间 |
| --- | ---: | ---: | ---: |
| 有效吞吐 | 4.49 MB/s | 5.86 MB/s | 0.767 [0.728, 0.875] |
| 往返 P99 | 23.82 µs | 17.50 µs | 1.361 [1.215, 1.633] |
| 服务端 CPU | 0.452 s | 0.286 s | 1.582 [1.398, 1.671] |
| 服务端自愿上下文切换 | 120,018 | 60,016 | 2.000 [1.9995, 1.9999] |

另取一个 120,000 帧诊断运行，在第约 150 ms 读取各线程的 `/proc` 计数。zrun 的独立 I/O 线程发生 11,005 次自愿切换，四个执行 worker 合计 11,015 次。Tokio 的切换集中在其运行时 worker。配对数据和线程采样一致指向独立 I/O 线程与执行线程的交接，但不能单独量化交接对每一条消息的延迟贡献。下一轮可直接验证由执行 worker 驱动 I/O 的拓扑。

原始记录和运行探针位于 `dist/zrun-tcp-handoff-paired.jsonl` 与 `dist/zrun-tcp-handoff-probe.py`。

## Pool worker 直接驱动 I/O

启用 `io` 后，`Pool::with_max_tasks_and_io` 将 poller 交给首个执行 worker。该 worker 在休眠时使用计时器剩余时间作为 poll 超时，在连续运行任务时也定期检查 I/O。CLI 的多 worker 默认模式仍使用专用 reactor。测试覆盖持续 runnable 的任务下 TCP 回显仍有进展，以及 Pool 关闭后 I/O handle 不再接收注册。全 feature、全 target 测试、严格 Clippy、无 feature 的 executor 检查和 rustdoc 通过。

四 worker，同一 Linux 主机、Rust 1.100.0 release、服务端 CPU 0–7、客户端 CPU 8–15。各格 12 对独立进程。运行两组对照共 192 个样本，帧校验均通过。表格为同一候选对早期 zrun 专用 reactor（`199cf79`）或 Tokio 1.54.1 的中位数比及 95% 配对区间。

## 命令服务使用 worker 驱动 I/O

在同一个新 CLI release 二进制上，用 `ZRUN_WORKERS=4`，分别选择 `ZRUN_IO_DRIVER=worker` 或 `thread`。相同 Linux 主机、Rust 1.100.0、CPU 0–15，500 个并发 Unix socket 客户端，每种负载 10 对交替运行。40 个独立 broker 样本全部核对了输出、请求 ID、实际执行次数和退出状态。复用负载每轮实际启动一次，独立执行每轮启动 500 次。

| 负载 | 吞吐比 | P99 比 | 峰值服务进程 RSS 比 |
| --- | ---: | ---: | ---: |
| 独立执行 | 1.004 [0.992, 1.010] | 0.991 [0.989, 1.005] | 0.999 [0.995, 1.002] |
| 同键复用 | 1.062 [0.935, 1.129] | 0.942 [0.885, 1.071] | 0.995 [0.995, 1.003] |

比值为 worker/thread 的中位数比及配对 bootstrap 95% 区间。两种负载的采样峰值线程数均由 7 降至 6，吞吐、P99 和 RSS 未检出稳定差异。服务默认继续使用独立 I/O 线程，worker 模式可显式启用。另实测 TCP Streamable HTTP 首次执行、stdio 经 Unix socket 命中同一 broker 缓存，以及在 worker 模式下捕获 stdout/stderr 和命令超时返回 124。

原始数据位于 `dist/zrun-cli-worker-io-load.jsonl`。

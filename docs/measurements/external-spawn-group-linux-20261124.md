# 多线程外部提交分组实验

对照为发行提交 `3c14040`，候选 `5a17b3d` 将外部提交从逐任务轮转改为每四个任务轮转。Linux x86_64，Intel Core i9-12900HX，固定 CPU 0–15，Rust 1.100.0。两份二进制均由干净提交用 `cargo build --offline --locked --release -p zrun-bench --bin zrun-bench` 生成。每格交替运行 10 对独立进程，任务规模 100,000，180 个样本全部通过。下表为候选/对照中位数比及配对 bootstrap 95% 区间。吞吐越大越好，P99 越小越好。

| Worker | 创建回收吞吐 | 自唤醒 P99 | 跨线程唤醒 P99 |
| ---: | ---: | ---: | ---: |
| 4 | 0.945 [0.858, 1.020] | 1.086 [0.903, 1.254] | 0.938 [0.784, 1.105] |
| 8 | 1.003 [0.982, 1.059] | 1.053 [0.888, 1.144] | 0.653 [0.000398, 557] |
| 16 | 1.006 [0.953, 1.075] | 1.065 [0.990, 1.176] | 1.069 [1.031, 1.245] |

三档创建回收区间均跨过 1，16 worker 跨线程 P99 区间整体变差，候选未合入。8 worker 跨线程 P99 区间太宽，无法判断方向。

补充运行一次 4 worker 百万任务创建回收，分别采样 zrun 和 Tokio 的用户态 CPU 周期。zrun 的 `SharedPool::next_task` 合计占报告总周期约 35%，提交线程的 `publish` 占约 8%。这些是单次采样的热点，尚不能区分 `next_task` 内部的抢占、队列锁争用与空队列扫描。下轮应先拆出这些路径的开销，再选择具体优化。原始报告和采样记录位于 `dist/zrun-spawn-group-*`。

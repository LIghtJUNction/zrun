# zrun 0.1.0-p0.2：任务登记实验与验收

本候选把活动任务登记从散列表改为连续引用数组，并在保留先前休眠优化的同一基线上测量这项改动。百万任务下，spawn/join 吞吐中位数提高 36.5%，自唤醒吞吐提高 59.6%，每进程 P99 自唤醒延迟的中位数降低 15.9%。其他规模的收益不一致；10 万任务的每任务增量 RSS 增加约 0.48%。完整结果见[机器可读记录](task-registry-linux-20261124.json)。

两组独立实验各完成 400 个新进程样本，均通过工作负载内的任务数量、结果身份、取消或退出状态检查。常规回归 45 项通过，另行显式运行的百万任务回归通过；核心 Miri 37 项、休眠协议 Loom 3 项、严格 Clippy 和格式检查通过。对 Tokio 1.54.1 的新比较中，20 个规模×指标单元只有 2 个同时通过普通与挑战门槛，均为空闲增量 RSS；其余门槛未通过。当前仍是未发布、未部署的私有 P0 候选。

## 实现为何改变开销

旧登记需要用任务编号计算哈希，再查找任务引用。新登记保存 `Arc<Task>` 的连续数组，任务对象记录数组位置；完成时用尾部元素填补空位，并在同一把登记锁内更新被移动任务的位置。数组移动的是引用，Future 本身的地址和唯一 poll 所有权不变。唤醒或完成入口仍检查真实对象身份，防止旧位置错误命中新任务。实现与边界见[任务登记设计](../task-registry.md)。

这个结构减少了热路径的散列操作，同时给每个 Task 增加了一个索引字段。因此，总内存取决于任务对象大小、数组容量、分配器和页粒度，不能仅由“去掉 HashMap”推导。现有结果正体现了这种权衡：三个规模的摊销 RSS 下降，10 万任务反而略增。该解释是基于实现与测量的推断；本轮没有做分配器或 CPU profile 归因。

百万任务时，每个 pending 任务的增量 RSS 从 355.672 B 降至 344.015 B，下降约 3.28%；10 万任务从 342.467 B 增至 344.105 B，增加约 0.48%。这里包含等待中的 Future、JoinHandle 和登记所需的进程驻留内存，不等于 Task 结构的 `size_of`。相同 RSS 读数产生零宽 bootstrap 区间，只表示这 10 次样本没有出现读数差异；页粒度及系统测量误差仍然存在。

空闲场景只创建 runtime，不提交对应数量的任务。它出现在各规模循环中，是重复的独立空闲采样，不能解释为“百万个空闲任务”的内存。空闲 RSS 的绝对量较小，也更容易受页粒度和分配器影响。

P99 列先在每个进程内计算 self-wake 延迟 P99，再对 10 个进程的 P99 求中位数。它不是合并所有延迟样本后的全局 P99。这个场景对排队顺序敏感：zrun 的 FIFO 队列把被唤醒任务放回队尾，其他已就绪任务会影响等待时间。TCP 与跨线程唤醒需要独立实验。

# Pool 批量提交

`Pool::spawn_batch` 和 `PoolSpawner::spawn_batch` 每批最多一起发布八项就绪任务，逐个检查容量，返回与输入对应的结果。输入迭代发生 panic 时，发布已接纳任务，避免它们滞留在任务登记表。批量提交用一次队列锁与通知发布一批，接纳仍逐个使用登记表。

Linux x86_64、Intel Core i9-12900HX、Rust 1.100.0 release、CPU 0–15。单个提交方以 4 worker 提交 100,000 个立即就绪的 Future，逐个等待并校验结果顺序。两种入口共用同一优化二进制，交替顺序运行 10 对独立进程。比值为批量/逐个提交的中位数比及配对 bootstrap 95% 区间。

| 指标 | 逐个 | 批量 | 比值 |
| --- | ---: | ---: | ---: |
| 提交耗时 | 109.5 ms | 48.4 ms | 0.442 [0.425, 0.470] |
| 提交及等待耗时 | 120.5 ms | 59.9 ms | 0.497 [0.473, 0.526] |

此实验覆盖库的两种入口。真实命令 broker、Tokio 和含 I/O 的任务需要各自测量。原始数据位于 `dist/zrun-batch-submit-probe.tsv`。

## 命令服务实测

对照 `34ec98c` 与候选 `5861ace` 均由干净提交用 `cargo build --offline --locked --release -p zrun-cli` 构建。相同 Linux 硬件与 CPU 绑定，`ZRUN_WORKERS=4`。候选把启动时的 32 个命令处理任务改为分批发布。

| 场景 | 对数 | 对照中位数 | 候选中位数 | 候选/对照及 95% 区间 |
| --- | ---: | ---: | ---: | ---: |
| 启动到 Unix socket 就绪 | 60 | 1.008 ms | 0.977 ms | 0.969 [0.950, 1.002] |
| 4,096 个复用请求完成 | 10 | 271.4 ms | 272.4 ms | 1.004 [0.952, 1.130] |

启动对照先预热六对，再用平衡顺序随机运行。就绪以服务打印 socket 路径且 socket 存在为准，每次均正常退出且删除 socket。负载对照交替顺序，每轮用最多 64 个并发客户端运行 512 个独立脚本。20 轮的 81,920 个请求全部返回预期数据，每轮底层命令只执行一次。

两个区间均跨过持平。批量提交在库微基准的收益没有转化为这里可检出的启动或端到端收益。当前接入只用于启动处理任务，进入服务的批量命令仍逐条通过授权和队列接纳。原始数据和启动脚本在 `dist/zrun-broker-{startup,load}-ab.*`。

## MCP 请求批量入队

在相同 Linux 硬件、CPU 0–15、4 worker 下，通过 Unix socket 发送 256 个 `shell_batch` 调用，每批 16 条命令，最多 32 个客户端并发。与此前逐条入队的 `5861ace` 比较。10 对独立进程每轮均校验 4,096 个结果，并确认底层命令只执行一次。中位耗时从 35.19 ms 到 35.19 ms，候选/对照比为 1.000 [0.905, 1.074]。这组样本只覆盖同键复用负载。原始报告位于 `dist/zrun-mcp-request-batch-probe.jsonl`。

补充混合负载使用相同的两份 release 二进制（`5861ace` 对 `52e99ba`）和运行条件。每批 16 条中有 2 条唯一命令和 14 条复用命令。每轮按输入顺序校验 4,096 个结果，另核对 512 条唯一命令实际各执行一次、共用命令实际执行一次。10 对样本的中位耗时为 111.64 ms 对 114.70 ms，候选/对照为 1.027 [1.000, 1.072]。原始样本位于 `dist/zrun-mcp-mixed-batch-probe.jsonl`。


响应通道改在队列锁外分配，单次调用的两个临时缓冲区在所有组之间复用。再次采用相同条件，各跑 10 对进程，所有结果和实际启动次数通过校验。原始样本位于 `dist/zrun-mcp-reuse-*.jsonl`。

## 缓存命中的直接交付

缓存命中直接返回已经就绪的结果，省去逐条创建和发送一次性通道。未命中的命令与在途订阅仍使用通道。相对 `ef248a2`，相同硬件及条件下各运行 10 对进程，共 163,840 条命令请求，全部通过结果、执行次数和退出状态校验。

| 混合负载 | 111.79 ms | 109.01 ms | 0.975 [0.952, 1.050] |

两个区间均跨过持平。原始样本位于 `dist/zrun-ready-cache-ticket-{same,mixed}.jsonl`。

## 锁外计算复用键哈希

候选在入队前算一次复用键哈希，缓存和在途表在锁内重复利用该哈希。键相等仍比较完整的脚本、目录、超时和复用参数。与 `4a6df78` 比较，在同一 Linux 主机固定 CPU 0–15、四 worker。通过 Unix socket 每批提交 16 条同键命令，每轮 4,096 条，全部返回预期结果且底层只执行一次。两种输入各测 10 对独立进程。

| 脚本 | 对照中位数 | 候选中位数 | 候选/对照及 95% 区间 |
| --- | ---: | ---: | ---: |
| 短脚本 | 33.11 ms | 33.17 ms | 1.002 [0.804, 1.087] |
| 含 8 KiB 注释 | 98.21 ms | 102.77 ms | 1.046 [0.863, 1.073] |

没有检测到稳定收益，候选未合入。大键仍需在命中时比较完整文本，本轮未分离比较、解析和传输的时延。补充探测中，同一批 16 条各带 24 KiB 注释的请求按现有限额返回 HTTP 413，未计入基准。候选通过 84 项测试及严格 Clippy。原始样本位于 `dist/zrun-prehash-{large,short}.jsonl`，实验改动位于 `dist/zrun-prehash-experiment.patch`。

## 登记锁竞争复测

在上节两个版本临时加同样的探针。分别统计首选分片接纳、确认全满的分片扫描、任务完成回收。探针先执行 `try_lock`，失败后才计时常规加锁，用线程本地计数，在任务结束后汇总。这里的等待时间是多个线程的总和，不能与进程墙钟时间直接相减。

4、8、16 worker，两种任务各测 10 对进程，共 120 个有效样本，环境与上节一致。候选的接纳加锁次数从每轮 100,000 次降至 12,500 次。未触发确认全满的扫描，两版均回收 100,000 个任务。下表为回收阶段探针报告的等待总时间中位数。

| Worker | 每任务自唤醒次数 | 对照 | 候选 |
| ---: | ---: | ---: | ---: |
| 4 | 0 | 14.88 ms | 14.90 ms |
| 4 | 16 | 5.55 ms | 8.06 ms |
| 8 | 0 | 13.68 ms | 12.83 ms |
| 8 | 16 | 5.54 ms | 6.59 ms |
| 16 | 0 | 19.38 ms | 20.58 ms |
| 16 | 16 | 8.72 ms | 10.16 ms |

8 和 16 worker 的接纳首轮 `try_lock` 失败中位数在 0–1 次，探针版本没有重现此前明显的端到端回退。随后用原有无探针的两份二进制再跑 40 对，8 和 16 worker 四格的回退均重现。例如 16 worker、每任务自唤醒 16 次的完成耗时中位数从 81.01 ms 增至 128.64 ms。探针改变了运行特征，不能用这些锁等待数解释无探针回退。下一步可在无探针的原二进制对照用户态周期，比较就绪队列、唤醒与任务回收路径。

实测数据和探针生成脚本位于 `dist/zrun-registry-count-*`。探针均未进入产品代码。

### 无探针周期采样

沿用原两份 release 二进制，在固定 CPU 0–15 上运行 16 worker、100,000 个任务、每任务 16 次自唤醒。每版采三次，所有任务结果校验通过。使用 `perf record -F 3999 -e cycles:u`，以下为 CPU 核用户态周期的估算，范围仅覆盖计数器实际记录的核和用户态代码。

| 指标 | 逐任务登记 | 合并登记 |
| --- | ---: | ---: |
| 报告周期总量中位数 | 18.69 亿 | 22.42 亿 |
| `SharedPool::next_task` 占比范围 | 58.82%–59.29% | 61.36%–63.00% |
| 据总量和占比估算的 `next_task` 周期中位数 | 11.05 亿 | 13.95 亿 |
| `Mutex::lock_contended` 占比范围 | 4.76%–5.00% | 2.48%–3.14% |

候选的取任务路径约多消耗 2.9 亿用户态周期，占两版本报告总周期中位数差的大部分。互斥锁的阻塞慢路径占比反而降低。采样支持优先检查 `next_task` 的本地取队列与窃取扫描，无法从函数级样本判定两者各自贡献。首对墙钟样本与后两对差异较大，三对周期采样不作为独立的墙钟性能验收。

原始 perf 数据和报告在 `dist/zrun-tokio-batch{,-registry}-probe-{1,2,3}.{perf,profile}`。

进一步对相同六份记录做指令级标注。将 `next_task` 内部分指令的周期样本比例乘以各次总周期和函数样本比例，得到以下中位数估算。原子操作在非精确采样中常记到紧随其后的指令，因此按相邻位置汇总。

| 指令位置 | 逐任务登记 | 合并登记 |
| --- | ---: | ---: |
| 本地队列获取和释放锁的后继指令 | 1.01 亿 | 0.97 亿 |
| 窃取扫描获取和释放锁的三个后继指令 | 7.75 亿 | 7.86 亿 |
| 入口处读取 worker 数后紧随的范围比较 | 约 27 万 | 1.88 亿 |

窃取锁相关指令是两版共同热点，计数近似持平，无法解释大部分新增周期。入口比较附近是新增热点，但当前事件没有精确指令定位，不能据此区分读取延迟、指令布局与采样偏移。详细标注位于 `dist/zrun-tokio-batch{,-registry}-probe-{1,2,3}.annotate`。

| ---: | ---: | ---: | ---: |
| 4 | 0 | 1.004 [0.954, 1.050] | 1.014 [0.967, 1.039] |
| 4 | 16 | 1.025 [0.942, 1.100] | 1.015 [0.944, 1.084] |
| 8 | 0 | 1.027 [0.918, 1.103] | 1.023 [0.936, 1.090] |

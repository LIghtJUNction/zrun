# p0.15 调度性能实测

四个后台 worker 接收一个外部线程逐个提交的 10 万个任务时，p0.15 的 spawn/join 吞吐是上一版主线的 2.31 倍，每个任务自唤醒 16 次的吞吐是 5.21 倍。同机 Tokio 1.54.1 的两项吞吐仍然更高。普通性能门槛尚未全部达到。

## 同机三方比较

Linux 6.18.57，x86_64，AMD EPYC 9V74，来宾可见 9 个逻辑 CPU。调度进程固定在 CPU 0–7。Rust 1.100.0，release，优化级别 3，无额外 RUSTFLAGS。基线是 `fcb2548877383518e597b74e2778c18918309fd4`，候选运行时是 `32c5ea5be7ccfcc48399a59c6294932038cff2d9`。每个配置 12 轮，每次启动独立进程，三种执行顺序及其反序循环两遍。缺少基线的辅助单元只运行两个引擎。按轮配对 bootstrap 5,000 次，表中为中位数之比和逐项 95% 区间。每个延迟进程在固定索引取最多 2,048 个时间样本。共享云机的其他负载及频率不可控。16 个 worker 共用 8 个 CPU。

## 尾延迟与调度策略

已有任务等待执行时，计算池可以把后续外部 spawn 的通知合并。取走工作或窃取任务的 worker 在进入用户 Future 前通知另一个空闲同伴。停车前最后一次检查会等待正在使用的计算队列锁，以免把暂时无法加锁当成队列为空。直接通过单线程 Runtime 提交任务时，Rust 借用规则保证驱动此刻不在运行，省去了发送停车通知的操作。跨线程 Spawner 保留原有通知。

16 worker、10,000 任务、四个提交线程的首次执行 P99 从 29.42 µs 增至 83.79 µs，候选 / 基线为 2.85 [1.88, 3.79]。同一候选在这个单元的 P99 中位数约为 Tokio 的 11%。单线程 Runtime、100,000 任务的跨线程唤醒 P99 也出现回退，候选 / 基线为 1.14 [1.03, 1.42]。这两个结果限制了对尾延迟改善的结论。

另一个候选用位图查找正在停车的 worker。在 16 worker、10,000 任务下，竞争提交 P99 相对当前实现为 0.91 [0.53, 1.31]。四 worker、100,000 任务下为 1.73 [0.15, 3.63]。两组均未确认改善，因此预览版继续使用队列间通知。初筛中还尝试了无界共享提交队列，四生产者的首次执行延迟上升，该实现已舍弃。

## 回环 TCP

16 个连接，每帧 256 字节，每连接预热 8 帧、测量 512 帧。服务端使用 CPU 0–3，双 worker 客户端使用 CPU 4–5，12 对独立进程。每帧验证回显字节。四 worker 的吞吐比为 0.94 [0.85, 1.11]，往返 P99 比为 1.02 [0.82, 1.30]。单 worker 的对应比值为 0.84 [0.64, 1.11] 和 1.11 [0.73, 1.36]。四个区间均跨过持平。

## 正确性与复现

云端 Linux 通过 78 项运行时及 I/O 测试，另行通过 release 百万任务回归、11 项 Loom 模型、47 项 Miri 单元测试以及工作区全目标全特性严格 Clippy。新增回归一次向同一队列发布四个会阻塞的任务，要求四个不同 worker 在释放屏障前全部开始执行，重复 16 轮。云沙箱禁止绑定具名 Unix socket，工作区 CLI 的相关用例在正式发布工作流的 Linux runner 验证。

在基线和候选主线提交分别运行 `cargo +1.100.0 build --locked --release -p zrun-bench`，保存各自的可执行文件。当前版本与 Tokio 的直接比较可按下列命令复现。原始样本采用独立进程，二进制和生成结果放在 Git 之外。

```sh
python3 scripts/benchmark.py --binary target/release/zrun-bench --output /tmp/zrun-result \
  --workers 4 --tasks 100000 --rounds 12 --bootstrap 5000 --latency-samples 2048 \
  --scenarios spawn_join yield contended_spawn wake_latency external_wake_latency pending_memory idle \
  --affinity 0-7
```

[三平台完整矩阵运行及原始数据](https://github.com/LIghtJUNction/zrun/actions/runs/46059547948)覆盖 1、2、4、8、16 worker 和四档任务规模。该工作流对应 `91bc8d387c6e6123fa3017bacb4547853dd37014`，相对上述候选只更新对照程序、统计校验、文档和工作流。工作流成功表示采样和正确性检查结束，门槛按每个报告的 `normal_pass` 判定。24 小时稳定性有单独的验收协议。

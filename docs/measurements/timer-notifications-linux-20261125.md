# 定时器队首通知

比较 `f25f1e0` 与 `6c3d50d` 的定时器驱动。Linux x86_64、Intel Core i9-12900HX、Rust 1.100.0 release，固定 CPU 2。每个进程注册 100,000 个未来 600 秒的定时器，确认全部保留，再按注册顺序或倒序取消并确认条目归零。每种方式 20 对进程，平衡后随机先后顺序。通知回调只增加一个原子计数。测量从注册开始到取消结束，统计不含驱动关闭。

| 取消顺序 | 对照通知次数 | 候选通知次数 | 对照总耗时 | 候选总耗时 | 耗时比及 95% 区间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 按注册顺序 | 200,000 | 100,001 | 31.76 ms | 31.72 ms | 0.999 [0.944, 1.029] |
| 倒序 | 200,000 | 2 | 38.89 ms | 37.54 ms | 0.965 [0.957, 0.985] |

所有样本均通过。注册顺序取消反复删除队首，每次都需要更新驱动；倒序只在首次注册和最终取消时改变队首。该微基准的回调未取代实际停车和唤醒，无从估算系统调用或应用侧收益。10 次无探针的工作线程取消回归验证了短定时器不会提前触发、长定时器取消后归零。源码和原始样本位于 `dist/zrun-timer-notify-probe.{rs,tsv}`。


## 真实工作线程的取消回归

相同两个提交各构建 `--release -p zrun --test pool`，固定 CPU 0–15，直接运行过滤后的测试二进制。20 对进程，平衡后随机先后，每次覆盖 1、4、16 worker，每档四轮，每轮取消 4,096 个已注册的长定时器，并等待 32 个短定时器正常触发。40 次均通过每个任务的返回值与截止时间、包含已注册定时器的队列回收检查。进程 CPU 时间来自 Linux 子进程资源统计。墙钟与 CPU 时间均含启动、唤醒和测试框架，未单独隔离定时器线程。

| 指标 | 对照 | 候选 | 候选/对照及 95% 区间 |
| --- | ---: | ---: | ---: |
| 墙钟耗时 | 155.85 ms | 154.10 ms | 0.989 [0.970, 1.005] |
| 进程 CPU 时间 | 402.11 ms | 386.89 ms | 0.962 [0.892, 1.043] |
| 内核 CPU 时间 | 167.83 ms | 178.72 ms | 1.065 [0.950, 1.168] |

原始样本位于 `dist/zrun-timer-workers-results.jsonl`。


## Tokio 对照

从 `b423cad` 构建，使用同一 release 二进制分别运行 `zrun::Pool` 和 Tokio 1.54.1 多线程运行时，CPU 0–15。每个进程逐个提交 16,384 个任务，每个任务首次 poll 一个 600 秒定时器且返回 Pending 后才计入已注册。确认全部注册后，从提交线程逐项取消，等待所有句柄返回取消结果。zrun 另确认可见定时器条目归零，Tokio 公共 API 没有对应计数。每档 20 对进程，平衡后随机先后，200 个样本均通过。比值为 zrun / Tokio 的耗时中位数比与配对 bootstrap 95% 区间。

| Worker | 创建任务并注册定时器 | 取消并等待任务 |
| ---: | ---: | ---: |
| 1 | 0.790 [0.764, 0.836] | 2.615 [2.458, 2.723] |
| 2 | 0.887 [0.788, 0.956] | 2.296 [2.005, 2.644] |
| 4 | 1.062 [1.022, 1.124] | 2.476 [2.223, 2.607] |
| 8 | 1.270 [1.171, 1.360] | 2.341 [2.145, 2.572] |
| 16 | 1.937 [1.721, 2.036] | 3.869 [3.581, 4.193] |

该对照包含任务调度、注册和取消，不能单独归因到定时器的数据结构。包含 1 worker 的多线程入口，与单线程 Runtime 不同。源码和原始样本位于 `dist/zrun-timer-tokio-probe.{rs,tsv}`。

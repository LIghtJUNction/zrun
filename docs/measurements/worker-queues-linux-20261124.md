# Linux 执行器队列与唤醒成本

基线 `503a2bd` 与任务归还候选 `ed136b4` 由 Rust 1.100.0 以 release 构建，在 Intel Core i9-12900HX、Linux 7.3.5-arch1-1 上运行。性能对照的进程固定在逻辑 CPU 0–15。每格 10 对独立进程，两版本运行顺序逐轮交替，区间为配对 bootstrap 95% 区间。

## 任务归还

执行器已经持有出队任务的 `Arc<Task>`。内联 poll 预算用完时，执行器将这份任务引用交还给原队列，省去弱调度器引用的升级、任务引用克隆，以及多 worker 路径的线程本地查询。原子状态仍只授予一次入队权。任务重新入队前，Future 已经放回任务内部。关闭仍可取消队列中和待归还的任务。

1、4、8 worker 在 10,000 和 100,000 tasks 跑完 spawn/join、唤醒吞吐和 CPU、自唤醒 P99、跨线程 P99，共 480 个正确性校验通过的进程样本。100,000 tasks 时的候选/基线比值如下。

| worker | 唤醒吞吐 | 进程 CPU / wake |
| ---: | ---: | ---: |
| 1 | 1.113 [1.078, 1.181] | 0.900 [0.846, 0.929] |
| 4 | 1.097 [1.006, 1.137] | 0.854 [0.819, 0.934] |
| 8 | 1.085 [1.024, 1.141] | 0.799 [0.685, 0.867] |

10,000 tasks 的 1、8 worker 也测得唤醒吞吐增长和 CPU 开销下降。两种 P99 的各格置信区间均跨过 1。多 worker 唤醒负载把提交计入计时，单 worker 在提交后开始计时，两个版本使用相同定义。

## 采样与队列实验

对 `ed136b4` 的另一趟运行做了 gprofng 2 ms CPU 时间采样。4 worker 固定在逻辑 CPU 16–22，100 万任务各自唤醒 64 次，全部校验通过。17.458 秒采样 CPU 时间中，`SharedPool::publish` 自身占 48.55%，`SharedPool::take` 自身占 23.89%，`Task::poll_budget` 自身占 11.72%。百分比仅描述该次采样负载。

固定批次候选 `517118f` 对比 `ed136b4`。2 worker、100,000 tasks 的唤醒吞吐为 1.312 [1.232, 1.440]。10,000 tasks 时，2 worker 的自唤醒 P99 升至 1.238 [1.016, 1.529]，4 worker 的跨线程 P99 升至 1.161 [1.004, 1.265]。固定批次未纳入主线。

128 字节对齐候选 `77e642c` 各 worker 单独放置就绪队列的互斥锁与索引。相比 `ed136b4`，1,000,000 tasks 的同配置单次采样中，`publish` 与 `take` 仍占 62.39% 的采样 CPU 时间。采样用于定位热点。下面的收益来自 2、4、8、16 worker 各 240 个独立进程样本的配对实测。

| worker | 任务数 | CPU / wake 比值 |
| ---: | ---: | ---: |
| 2 | 100,000 | 0.920 [0.846, 0.990] |
| 4 | 10,000 | 0.914 [0.885, 0.976] |
| 8 | 100,000 | 0.788 [0.726, 0.932] |
| 16 | 100,000 | 0.842 [0.787, 0.963] |

4 worker、100,000 tasks 的 spawn/join 吞吐提高到 1.066 [1.010, 1.131]。16 worker、100,000 tasks 的跨线程 P99 样本分成约 3–4 μs 和数十 ms 两组，波动不能解释成确定的数量级收益。16 worker、10,000 tasks 的空闲增量 RSS 比值为 1.197 [0.996, 1.265]，对齐所用的额外空间需要在完整内存矩阵里复核。只把环形索引改为切片遍历的候选 `9604559` 在 4、8 worker、100,000 tasks 均未测得稳定改善，未纳入主线。

## 同一源码对 Tokio 1.54.1

对 `77e642c` 扩到 1、2、4、8、16 worker、100,000 tasks。共 600 个独立进程通过校验。以下为 zrun/Tokio 的中位数比值。吞吐越高越好，CPU 和 P99 越低越好。

| worker | spawn/join 吞吐 | 唤醒吞吐 | CPU / wake | 跨线程 P99 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.631 | 0.893 | 1.119 | 2.447 |
| 2 | 0.389 | 0.458 | 2.318 | 1.845 |
| 4 | 0.300 | 0.216 | 3.944 | 1.869 |
| 8 | 0.299 | 0.359 | 2.215 | 1.810 |
| 16 | 0.313 | 0.299 | 3.345 | 见亲和复测 |

所有五档的自唤醒 P99 和单 worker 空闲增量 RSS 通过普通目标。其他内存配置和全部 spawn/join、唤醒吞吐及 CPU / wake 仍未达到目标。

16 worker 的跨线程 P99 在 CPU 0–15 下出现微秒与数十毫秒两组样本，脚本给出领先。将同一二进制的亲和范围扩大到 CPU 0–22 后，10 对样本的中位数为 zrun 54.166 ms、Tokio 36.290 ms，比值 1.493 [1.421, 1.725]。跨线程 P99 未达到可复现的领先，验收采用保守结论。

TCP 回环用 1、4、8 worker 和四组连接数及帧长，共 240 个独立样本通过回显校验。24 格中 3 格通过严格领先门槛，均为 8 worker。

| 连接 × 帧长度 | 指标 | zrun / Tokio |
| --- | --- | ---: |
| 64 × 64 B | 往返 P99 | 0.646 [0.508, 0.716] |
| 128 × 4 KiB | 往返 P99 | 0.699 [0.478, 0.798] |
| 32 × 64 KiB | 吞吐 | 1.175 [1.037, 1.364] |

服务端固定在 CPU 0–7，客户端固定在 CPU 8–15。三个用例再分别与原子任务状态版 `9c6503d` 做直接配对，60 个样本通过校验，吞吐与 P99 各格区间均包含 1。Tokio 对照结果不能归因于本轮队列改动。

## 正确性与长测

`77e642c` 通过 66 项工作区测试、格式检查、严格 Clippy、rustdoc，以及 6 项 Loom 模型。另显式运行单 worker 百万任务测试，8 worker 独立进程也验证 1,000,000 次 spawn/join、校验和 499999500000、剩余任务 0。MCP 2025-11-25 通过官方 SDK 的 Unix、TCP 与 stdio 转发。Unix 千并发在 `live` 下确实执行 1,000 次，在 `reuse` 下执行 1 次并合并 999 次。zguard 测试覆盖读缓存前的准入，zplugin 示例验证放行和拒绝，实际命令保留 zmem scope。

长测脚本现在把选定的 worker 数传给比较器，并核对最终事件中的数量。两种引擎在 1、2、4、8、16 worker 共 10 个短跑均通过。以 `77e642c` 运行时二进制开启了 CPU 18–22 的四 worker 24 小时长测。此负载只覆盖 spawn、yield、join 和每批任务清零，完成状态及 RSS 斜率待核验。

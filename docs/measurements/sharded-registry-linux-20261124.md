# Linux 多线程任务登记分片

基线 `a804efe`，候选 `e9726e2`。Intel Core i9-12900HX，Linux 7.3.5-arch1-1，Rust 1.100.0 release。调度样本固定 CPU 0–15 串行运行。每格使用交替先后顺序的独立进程。表中区间为配对 bootstrap 95% 区间。

## 登记和退出

每个任务在一个登记分片保存一条薄引用。任务的 ID 低 8 位固定所属分片。窃取和远程唤醒只移动就绪任务，完成回收通过 ID 回到原分片。各分片的缓存行分开。未满时每次提交只取一个登记锁。优先分片满后可以借用其他分片。全部看似已满时按固定顺序取得登记锁，确认同一时点的全局容量。被拒绝的 Future 在锁释放后析构，可以安全重入。

关闭先停止接收新任务，再逐分片分离登记表。已经持有分片锁的提交由关闭线程收集。后续提交在同一分片锁内读到关闭标记。所有登记引用分离后，先停止定时器与唤醒 worker，再终止未完成任务。正在 poll 的任务继续遵守原任务状态机。

旧版 4 worker、百万任务的创建与回收采样中，回收登记及其子调用占 17.52% 的 CPU 样本，就绪任务选取和系统调用各约三成。本轮单独验证登记分片。单次 profile 用于定位，吞吐和开销以重复进程对照为准。

分片后在同类 4 worker 创建与回收负载复采样，登记回收及子调用约占 3.7%，就绪任务选取约占 40%，系统调用约占 29%。自唤醒负载中，队列发布与选取合计约占 50% 的排他 CPU 样本。两次采样用于确定后续优化位置。

## TCP 对照

服务端和客户端分别固定 CPU 0–7 与 8–15。分别对主线和 Tokio 各做 240 个独立样本，均通过回显校验。相对主线，单 worker、128 连接 × 4 KiB 吞吐为 1.063 [1.009, 1.126]，其余指标未检出稳定变化。对 Tokio 的 24 个指标格有 2 个过线，分别是 8 worker、64 连接 × 64 B 和 128 连接 × 4 KiB 的往返 P99，比值为 0.691 [0.611, 0.794] 与 0.636 [0.574, 0.754]。单连接 64 B 的 4 和 8 worker 吞吐都约为 Tokio 的 75%。

## 任务规模和正确性

在 4 worker 的补充对照中，10,000 与 1,000,000 任务的创建与回收吞吐比值分别为 1.201 [1.149, 1.299] 和 1.137 [1.032, 1.190]。三个补充规模的唤醒吞吐均上升，每次唤醒的 CPU 开销均下降。1,000 任务的创建与回收区间仍跨过持平。

候选通过 73 项常规测试、11 项 Loom、38 项 Miri、严格 Clippy 和 rustdoc。Miri 工具链为 `nightly-2026-11-24`。8 路提交争用 19 个名额的回归覆盖全局容量、取消与空位回收。之后加跑 7 项 Pool release 测试，其中并发提交与关闭的竞争用例重复运行 20 次。补充只涉及测试，基准及命令服务二进制来自候选 `e9726e2`。

单 worker 与 8 worker 的百万任务通过。8 worker 30 秒测试完成 12,250,000 项，活跃任务清零。4 worker 的 24 小时长测已启动，等候完整时长和 RSS 判定。完整任务规模矩阵与跨平台验收仍在进行。

官方 MCP SDK 通过 stdio 转发、TCP 和 Unix socket。zmcpio 0.5.3 从默认 Unix socket 完成初始化、工具发现和实际调用。8 worker 的千并发 Unix 复用测量记录一次实际执行和 999 次请求合并。真实 PTY、zmem scope、zplugin 和 zguard 的规则执行均通过。核心及 CLI 的常规依赖图无 Tokio。
